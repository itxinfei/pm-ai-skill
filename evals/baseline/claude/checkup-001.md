写不了——你手里这份"功能"到底是什么，一个字都没贴出来。"老板说要做"只说明了需求来源，功能本身、为什么做、给谁用全是空的，这时候硬写 PRD 就是高效地做错事。

先补这 5 项，能答多少答多少，答不上来的标"不知道"，我会把它放进 PRD 的待确认项：

**必答（没有这三项不动笔）**

1. **功能是什么**：一句话说清要做的东西，加上老板的原话或聊天记录截图。老板说的是方案（"做个签到"）还是问题（"留存太差想办法"），这两种写法完全不同。
2. **为什么现在做**：老板想解决什么问题、有没有期望的指标（比如"次月留存提到 40%"）。没有指标的 PRD 写不出验收标准。
3. **谁在用、现在怎么解决**：目标用户是谁（新用户/老用户/付费用户？C 端还是 B 端？）；这个问题他们今天靠什么办法绕过去。说不出旧方案，大概率是伪需求。

**顺手给了能少返工的**

4. **形态和约束**：App / 小程序 / Web / 后台？期望上线时间、谁提的 deadline。
5. **已有材料**：竞品截图、老板转发的文章、客服反馈、数据报表——有就贴，没有就说没有，我不编。

补完之后我不会直接甩 PRD 全文，先给你一张**需求体检卡**（六个必答：使用频率、不做会怎样、成功怎么量、风险、有没有更便宜的做法、谁维护），结论是"做"才进入 PRD；结论是"不做或先验证"，你拿着体检卡回去跟老板对齐，比拿一份 PRD 去被打回来强。

这个输出哪里需要调整？比如你们内部有固定 PRD 模板，或者时间很紧只能出简版，告诉我。
